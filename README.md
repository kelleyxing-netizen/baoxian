# 青禾报销助手

面向公司员工的报销事务智能体。把**规则性咨询**（制度、标准、材料）交给助手，
把**只能由人做的判断**（业务事实核对）留给人。

> 需求主线：员工先自助查**有效**制度 → 按制度提交相应材料 → 进入报销流程后，
> 扩展为**经授权**查询**本人**单据状态。
> 分工约束：**制度由行政专员维护**，**业务事实仍由周敏核对**。

## 快速开始

无第三方依赖，Python 3.10+ 即可。

```bash
python run.py demo      # 跑完整剧本：四条工作流 + 三条边界
python run.py           # 交互对话，可用 /user E1001 切换身份
python -m unittest discover -s tests    # 30 条回归测试
```

`run.py` 默认在 `data/` 的临时副本上运行，不会污染样例数据；
指定 `--data ./data` 才会写回 `tickets.json`。

`demo` 模式会先打印工具契约与"明确不提供的动作"，再依次演示：

| 身份 | 提问 | 看点 |
|---|---|---|
| 张三（员工） | 我要报销上海出差的费用，9月12日，3860元，材料 TR-01… | 三步流程：有效制度 → 材料清单 → 提交并在周敏核对前不越位 |
| 张三 | QH2026090001 到哪了 | 本人单据，含节点、流转记录、下一步、时效提示 |
| 张三 | 帮我查一下李四的单据 QH2026090042 到哪了 | 经委派代查，答复写明授权依据 |
| 王五（外包） | 我的单据 QH2026090033 到哪了 | 有单据 ≠ 有权查：账号未开通该功能 |
| 李静（行政） | QH2026090001 到哪了 | 角色不交叉：能维护制度，但看不到员工单据 |

## 目录结构

```

  models.py                领域模型：制度、材料、单据、用户、审计事件
  store.py                 数据访问层（JSON → 可替换为真实系统接口）
  auth.py                  角色、权限范围、委派与对象级校验
  policy.py                制度库：有效性判定、检索、维护（仅行政专员）
  material.py              材料清单生成与缺项比对
  ticket.py                发起单据、经授权查询本人单据状态
  audit.py                 审计留痕

docs/                      需求、方案、工具契约、分期验收、风险
```

## 设计要点

**制度有效性靠机算，不靠模型记忆。** 制度带 `status`、`effective_from/to`、版本与维护人；
有效性按业务发生日判定，废止不等于追溯失效——2024 年发生的差旅仍依据当时的 V2.0，
而不是尚未生效的 V3.0。检索时费用类别是硬过滤，避免"问采购、答差旅"的串档。

**权限在后端，不在提示词。** 实际权限 = 角色范围 ∩ 智能体能力上限 ∪ 有效委派，
单据再叠加对象级校验（本人 / 委派 / 该单据的事实核对责任人）。
智能体能力上限里刻意**没有** `facts:verify` 与 `ticket:review`：
业务事实可读不可判，流程可查不可推。

**分工写在代码里。** 制度维护要 `policy:write`（行政专员）；`record_facts_verification`
存在但只抛边界说明（业务事实归周敏）。任何试图"顺手帮用户判断一下"的改动都会在测试里失败。

**审计覆盖四类事件。** 制度变更、单据查询（含被拒）、助手发起的写操作、越权尝试。

**时钟可注入。** 测试固定基准日，回归结果不随日历漂移。

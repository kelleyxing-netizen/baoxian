# 工具契约与平台移植

工具契约是智能体能力的**唯一清单**：模型能做什么，取决于这里注册了什么，
而不取决于提示词怎么描述。落地到任何平台时，把 `tools.TOOL_SPECS` 逐条翻译成
该平台的插件/工具定义，`ToolRegistry` 里的既有实现直接作为后端函数。

## 1. 工具清单

| 工具 | 权限范围 | 读/写 | 说明 |
|---|---|---|---|
| `search_policy` | `policy:read` | 读 | 按类别或自然语言检索有效制度，返回引用、效力理由与条款；同时返回命中但不可用的制度及原因 |
| `get_material_checklist` | `policy:read` | 读 | 按制度引出的材料集生成清单并比对缺项；条件项仅在可机械判定时判定 |
| `create_reimbursement_draft` | `reimburse:submit` | 写 | 以本人名义创建报销单草稿；不接受代他人发起 |
| `submit_reimbursement` | `reimburse:submit` | 写 | 草稿提交进流程，进入部门审核 |
| `my_reimbursement_status` | `ticket:read:self` | 读 | 本人单据状态、节点、流转记录、下一步、时效提示 |
| `list_my_reimbursements` | `ticket:read:self` | 读 | 列出当前身份可查看的单据（本人 + 已授权代查） |
| `my_review_queue` | `ticket:read:any` | 读 | 业务事实核对责任人的待核对队列（只含单号、类别、金额、节点） |
| `maintain_policy` | `policy:write` | 写 | 制度发布/修订/废止，保留版本历史并写审计 |
| `policy_ledger` | `policy:write` | 读 | 制度台账：每条制度的当前效力、版本、维护人、失效原因 |

## 2. 工具声明格式（平台中立）

```python
ToolSpec(
    name="my_reimbursement_status",
    description="查询本人单据的流转状态…仅限本人；他人代查需本人在系统内出具的未过期授权。",
    scope=SCOPE_TICKET_READ_SELF,
    parameters={"doc_no": {"type": "string", "description": "单据号", "required": True}},
    returns="状态、当前节点、流转记录、下一步、时效提示",
    boundary="不下结论、不催办、不修改单据；越权查询会被拒绝并留痕",
)
```

`ToolSpec.to_platform_dict()` 输出 JSON-Schema 子集
（`type` / `properties` / `required` / `additionalProperties` / `enum`），
可直接改写为 OpenAI tools、扣子插件或 Dify 工具定义。

**每个写工具都必须声明 `scope`**，`ToolRegistry.call` 在调用处理器之前统一校验，
鉴权失败在进入业务逻辑前就返回，处理器代码里不需要再写权限判断。

## 3. 明确不提供的动作

`tools.NOT_PROVIDED` 是刻意留空的清单，写进代码、文档与测试，防止后续被"顺手"加上：

| 动作 | 为什么不提供 |
|---|---|
| `verify_business_facts` | 业务事实核对（票据真伪、事由真实性、金额是否合规）由周敏在财务系统完成 |
| `approve_ticket` | 审批或推进单据流程由部门负责人、财务在各自系统完成 |
| `query_others_ticket` | 查询他人单据明细——仅本人或被授权人，核对责任人只能看队列 |

`TicketService.record_facts_verification` 存在但**只抛边界说明**，这样任何试图
"顺手帮用户核对一下事实"的改动都会立刻在测试里失败
（`test_agent_cannot_verify_business_facts`）。

## 4. 平台移植要点

### 4.1 制度不要只放向量库

制度必须**结构化存储**（版本、`status`、生效期、责任人），检索走结构化过滤，
向量检索只能作为"条款文字召回"的补充。原因：有效期与版本是硬约束，
向量相似度无法回答"这条现在还有效吗"，而错误地引用废止制度是本项目最严重的失败模式。

### 4.2 鉴权必须在后端

无论平台是扣子、Dify 还是自研，工具函数的入参都必须携带**已验证的调用者身份**，
由后端重新计算权限。不要依赖：
- 提示词里的"你只能查询本人的单据"；
- 前端传入的 `user_id`（可伪造）；
- 知识库里的权限说明文档。

### 4.3 提示词与代码的职责划分

| 放在提示词 | 放在代码 |
|---|---|
| 语气、格式、先结论后依据 | 权限范围、角色判定 |
| 边界的话术（怎么委婉拒绝） | 是否允许（布尔判断） |
| 意图与槽位的抽取 | 制度有效性判定、材料条件判定 |
| 需要引用制度的指令 | 引用从哪里取 |

### 4.4 换用大模型 Planner

```python
class LLMPlanner:
    """让模型只输出 {"intent": ..., "slots": {...}}，其余逻辑全部复用。"""
    def route(self, principal, text, context) -> Route: ...
```

约束模型输出：`intent` 必须是枚举值，`slots` 必须符合已知字段。
未知 intent 一律回落到 `policy_query`。工具调用的参数由代码从 `slots` 组装，
**不让模型直接拼工具 JSON**，避免参数注入。

### 4.5 真实系统对接

`store.Repository` 是唯一的数据访问层，逐个替换即可，上层无需改动：

| 原型 | 真实系统 |
|---|---|
| `data/policies.json` | 行政制度管理系统 / 企业知识库 API |
| `data/materials.json` | 与制度同源的配置中心 |
| `data/tickets.json` | 费控/报销系统单据接口 |
| `data/users.json` | 统一身份认证 + HR 主数据 |

替换时必须保持两点：单据查询接口**按调用者身份过滤**（不要把全量数据取回本地过滤），
制度接口**返回版本与生效期字段**（不要让助手自己推算）。

## 5. 系统提示词

见 `src/qinghe/agent.py` 的 `SYSTEM_PROMPT`。要点：

1. 只依据当前有效制度回答，必须给出文号、版本、生效期与条款号；
2. 检索到但不可用的制度必须说明"不可作为依据"及原因；
3. 业务事实由周敏核对，不判定、不代签、不催办、不承诺结果；
4. 制度维护只能由行政专员操作，其他角色只能建议提交修订申请；
5. 不能替他人发起报销，不能查询他人单据明细；
6. 没有有效制度可依据时，明确说"无有效制度"。

# 方案设计

## 1. 分层架构

```
                        ┌──────────────────────────────────────────┐
   员工 / 行政专员 / 周敏 │           对话入口（CLI / 平台）           │
                        └───────────────────┬──────────────────────┘
                                            │ 身份令牌（Principal）
                        ┌───────────────────▼──────────────────────┐
                        │  agent.py  对话编排                       │
                        │  意图路由 → 槽位补全 → 工具调用 → 带引用答复  │
                        │  Planner 接口：规则版 / 大模型版可互换        │
                        └───────────────────┬──────────────────────┘
                                            │
                        ┌───────────────────▼──────────────────────┐
                        │  tools.py  工具契约（9 个工具 + 能力边界）   │
                        │  每个工具声明 scope；调用前统一鉴权           │
                        └───────────────────┬──────────────────────┘
        ┌───────────────┬───────────────────┼───────────────────┬───────────────┐
        ▼               ▼                   ▼                   ▼               ▼
   policy.py       material.py          ticket.py            auth.py        audit.py
   制度库/有效性     材料清单/条件项       单据/授权查状态      角色/范围/委派    审计留痕
        └───────────────┴───────────────────┴───────────────────┴───────────────┘
                                            │
                        ┌───────────────────▼──────────────────────┐
                        │  store.py  数据访问层（JSON → 真实系统接口） │
                        │  制度库 / 材料 / 单据 / 用户（可逐个替换）    │
                        └──────────────────────────────────────────┘
```

分层的关键约束：**权限判断只发生在 `auth.py` 与 `tools.py`，绝不在提示词里。**
换大模型、换平台都不改变授权结论。

## 2. 权限模型

### 2.1 两层校验

```
实际可用范围 = base_scopes(角色) ∩ AGENT_MAX_SCOPES ∪ 他人对我的有效委派
                     ↑ 第一层：功能级（能不能用这个功能）
对象级（仅单据）：本人 ∨ 有效委派 ∨ 本人是该单据的事实核对责任人
                     ↑ 第二层：能不能看这条数据
```

只有第一层会退化成"能查所有人"，所以查询本人单据必须两层都过：
`ticket:read:self` 决定"能不能查"，`subject == 登录人` 决定"能查谁"。

### 2.2 智能体能力上限

`auth.AGENT_MAX_SCOPES` 显式收窄智能体能做的事：

| 权限 | 是否在智能体上限内 | 理由 |
|---|---|---|
| `policy:read` / `material:read` | ✅ | 咨询类，读操作 |
| `policy:write` / `material:write` | ✅ | 行政专员本就是制度责任人，助手只是他的操作渠道，仍受角色校验与审计 |
| `reimburse:submit` | ✅ | 以本人名义发起，不可代他人 |
| `ticket:read:self` | ✅ | 本人单据查询 |
| `ticket:read:any` | ✅（仅解锁队列） | 周敏看"待我核对"，看不到他人单据明细 |
| `ticket:review` | ❌ | 流程审批在各自系统完成 |
| `facts:verify` | ❌ | **业务事实只能由周敏在财务系统核对** |

### 2.3 角色—权限矩阵

| 角色 \ 权限 | policy:read | policy:write | material:read | reimburse:submit | ticket:read:self | ticket:read:any | facts:verify |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| 员工 employee | ✅ | — | ✅ | ✅ | ✅ | — | — |
| 行政专员 admin_specialist | ✅ | ✅ | ✅ | — | — | — | — |
| 财务核对人 reviewer | ✅ | — | ✅ | — | — | ✅ | ✅（系统内） |
| 外包 contractor | — | — | — | — | — | — | — |

行政专员有制度维护权但**看不到员工单据**；财务核对人有权核对事实但**不能通过助手改制度**。
互不交叉是刻意的：谁维护规则、谁核对事实、谁只能查询，三者分离。

### 2.4 委派

`data/users.json` 的 `delegations` 表达显式授权：`grantor` 允许 `grantee` 在
`expires_on` 之前以其名义查询单据，且必须有 `approved_by`。委派有到期日，
过期即失效，每次代查都会把授权内容写进答复（"经 E1002 授权代查（2026-09-01 起，2026-12-31）"）
与审计。

## 3. 制度库

### 3.1 数据模型（`models.Policy`）

| 字段 | 作用 |
|---|---|
| `policy_id` / `doc_no` / `version` | 唯一标识与对外引用（文号+版本） |
| `status` | `draft` / `published` / `repealed` |
| `effective_from` / `effective_to` | 效力区间；`to` 为空表示长期有效 |
| `category` | 费用类别，**检索时作为硬过滤** |
| `owner` | 维护责任人（行政专员） |
| `clauses[]` | 条款号 + 条文 + 标签 |
| `material_set` | 引用材料清单，实现制度与材料的解耦 |
| `supersedes` | 版本继承关系 |

### 3.2 有效性判定（`Policy.effectiveness`）

| 情形 | 结论 | 给用户的理由 |
|---|---|---|
| `status = draft` | 不可用 | 草稿状态，尚未发布（拟 X 起生效） |
| `on < effective_from` | 不可用 | 尚未生效，自 X 起适用 |
| `on > effective_to` | 不可用 | 已废止／已过有效期，效力止于 X |
| 区间内且 `repealed` | **可用** | X 在业务发生日有效（…，现已废止） |
| 区间内且 `published` | 可用 | X 有效（Y 起…） |

**关键设计：废止 ≠ 追溯失效。** `effective_to` 界定效力区间，废止只是宣布区间不再延续。
所以 2024 年发生的差旅仍然（且只能）依据 V2.0——V3.0 当时尚未生效。
这避免了"新制度追溯旧业务"这一最常见的报销口径错误。

**基准日的选择**：员工问"现在怎么报"用今天；问"X 月那笔怎么报"用业务发生日。
演示中"疫情防控期间交通补贴"按今天判定即为过期，会明确告知不可作为依据。

### 3.3 检索策略（`PolicyLibrary.search`）

1. 先用关键词表识别费用类别（差旅/招待/采购/交通补贴）；
2. **类别一旦确定就是硬过滤**——否则"问采购、答差旅"的串档会出现（"报销"这种通用词会让
   所有类别都命中）；
3. 命中结果里**有效制度优先**返回；命中但不可用的单独成列并附原因。

第 2、3 条是回归测试锁住的行为（`test_switching_category_resets_slots`、
`test_draft_policy_would_block_purchase_reimbursement`）。

### 3.4 维护流程（仅行政专员）

| 动作 | 语义 |
|---|---|
| `publish` | 发布新制度；若指定 `supersedes`，旧版同时置为废止并把 `effective_to` 设为新版生效日 |
| `revise` | 修订 = 生成新版本 + 旧版按期终止；**不覆盖历史** |
| `repeal` | 废止并记录原因 |

三种动作都落审计（谁、何时、改前改后、生效期），并可在制度台账中查看每条制度的当前效力与失效原因。
修订在生效日之前不会改变现行依据：`test_admin_can_revise_and_history_is_kept` 验证了
2026-10-20 仍用旧版、2026-11-02 才切到新版。

## 4. 材料清单

制度通过 `material_set` 引用材料集，两者解耦：行政专员改制度时不需要动材料库，反之亦然。

清单项分两类：

- **必需项（required）**：缺一不可，缺失即阻塞提交；
- **条件项（conditional）**：仅在条件成立时需要。条件判定分两种——

| 条件类型 | 例子 | 处理方式 |
|---|---|---|
| 可机械判定 | 逾期超过 30 日 → `TR-05`；单笔 ≥ 2000 元 → `PR-04` | 由 `MaterialCatalog._condition_rule` 按已知字段自动判定 |
| 需业务事实 | 是否超标、票据是否真实 | 返回 `None` → 标记"待确认条件项"，**不猜结论** |

"人均 260 元"这类输入只作为标准判断依据（`per_capita`），不会被误当成申报金额，
验收测试 `test_per_capita_is_not_treated_as_claim_amount` 锁住了这一点。

## 5. 单据与状态查询

### 5.1 生命周期

```
草稿 ──提交──▶ 部门审核 ──▶ 财务复核 ──▶ 出纳付款 ──▶ 归档/已入账
                  ▲
              助手在这里创建并提交（也只能提交本人单据）
```

`facts_verified` 是单据上的独立标记，只有周敏能置位，与流程节点无关——
**流程走得再快，也不代表事实已被核对。**

### 5.2 查询授权（`TicketService.status`）

```python
_require_ticket_read(principal)        # 第一层：账号是否开通该功能
_must_own(principal, ticket)           # 第二层：本人 / 有效委派 / 核对责任人
```

拒绝时：抛 `AuthError` + 写审计（含被拒对象与原因）。三种典型结果：

| 场景 | 结果 |
|---|---|
| 张三查自己的单据 | 允许，访问依据"本人单据" |
| 张三查无授权的他人单据 | 拒绝，审计记录"越权尝试：单据属于 E1003" |
| 张三查李四已授权代查的单据 | 允许，访问依据"经 E1002 授权代查（…，2026-12-31）" |
| 王五（外包）查自己的单据 | 拒绝，"账号尚未开通该功能"——**有单据 ≠ 有权查** |
| 行政专员查员工单据 | 拒绝，角色不交叉 |

### 5.3 状态答复包含

当前状态与节点、完整流转记录、下一步提示、时效提示（业务发生日距今天数与 30 日时限）、
材料齐备性提示、访问依据，以及"业务事实待周敏核对"的明确标注。

## 6. 对话编排

### 6.1 意图

`policy_query`（查制度+材料，主流程）、`reimburse`（发起报销）、`ticket_status`、
`business_fact`（边界回复）、`policy_admin`、`policy_ledger`、`review_queue`、`help`。

### 6.2 主流程三步

1. **有效制度**：命中则给出引用、效力说明与相关条款；无有效制度则停止，附不可用原因与转人路径；
2. **材料清单**：按制度引出的材料集比对已交材料，列出缺项与待确认条件项；
3. **提交**：缺项则阻塞；齐备且已知金额时，创建草稿→提交，返回单号与"事实仍由周敏核对"的说明。

### 6.3 槽位与话题隔离

费用类别、业务发生日、金额、人均金额、材料编码、单号从自然语言抽取。
**切换费用类别即视为新话题**，上一轮的金额/日期/材料全部丢弃
（`test_switching_category_resets_slots`）。没有这层隔离，上一轮差旅的 3860 元
会被算进这一轮的招待报销——这是多轮助手最隐蔽的一类错误。

### 6.4 大模型接入

`Planner` 协议只有 `route(principal, text, context) -> Route` 一个方法。
换成大模型实现时，让模型输出 `{"intent": ..., "slots": {...}}` 即可，
鉴权、工具调用、留痕、渲染逻辑完全复用。提示词见 `agent.SYSTEM_PROMPT`，
其中把职责与**边界**写死，但真正的约束在后端。

## 7. 审计

`audit.AuditLog` 记录四类事件，JSONL 落盘：

| 动作 | 记录内容 |
|---|---|
| `policy.publish` / `policy.revise` / `policy.repeal` | 谁改的、改前改后、生效期、原因 |
| `ticket.status.read` | 谁查了谁的单据、依据什么授权（含**被拒**记录） |
| `ticket.create` / `ticket.submit` | 助手发起的写操作及其制度依据 |
| `policy.maintain` / `auth.require` / `facts.verify` | 越权尝试，一律 `denied` |

拦截失败也必须留痕，否则"谁试过查别人的单子"就查不出来了。

## 8. 与人的分工（实现层面的对应）

| 事项 | 责任人 | 系统实现 |
|---|---|---|
| 制度的新增/修订/废止 | 行政专员李静 | `policy:write` 校验 + 版本与生效期 + 审计 |
| 业务事实核对 | 周敏 | `facts:verify` 不在智能体上限内；`record_facts_verification` 只抛边界说明 |
| 材料是否真实合规 | 周敏 | 智能体只做"清单 vs 已交"的机械比对 |
| 审批与付款 | 部门负责人/财务 | 无对应工具，助手不提供 |
